# Android 微信群定时转发：实现方案与交付策略

调研日期：2026-10-15，Asia/Shanghai。目标：从指定源群取得短剧推广消息，在约定时间自动发往已配置的目标群，减少每天的重复操作。

**最新需求已扩展为“一台电脑群控多台手机”，当前群控方案见 [android-phone-fleet-plan.md](android-phone-fleet-plan.md)。本文保留为纯手机独立运行的备选方案，预算也仅对应纯手机版本。**

纯手机路线选 AutoJs6，提供手机内配置页、每日定时、微信操作和本地任务记录。先用一台客户实际手机和 10 个目标群验证，再适配其他机型。

本文区分已核实的框架能力与待实测的微信操作。未连接客户设备，不能把方案中的流程描述为已跑通。报价建议是工作量估算，不是市场价格调查。

## 1. 先明确真正要转发的对象

客户口中的“链接”可能是不同消息。源消息类型应在验证阶段确定，不能全部按复制 URL 处理。

| 源消息 | 首选实现 | 要验证的内容 |
| --- | --- | --- |
| 带完整 URL 的文字 | 读取文字，原样发送；需要时也可原生转发 | URL 参数、中文、换行、表情是否完整 |
| 网页分享卡片 | 定位原消息，使用微信原生“转发” | 目标群中的标题、封面、落地页是否保持 |
| 小程序或短剧分享卡片 | 优先原生转发该消息 | 当前微信版本是否提供可用的转发入口、接收后的打开路径 |
| 截图、视频、二维码等 | 单独确认需求后适配 | 首版不自动把它们识别为普通链接 |

短剧推广 URL 的查询参数可能参与推广归属。文本方式应保留完整原文，不随意删除参数、不展开短链接、不自动改写内容。卡片是否保持推广归属，需要用客户实际样本验收，不能仅看标题一致。

如果客户每天已经能取得推广内容，也可以直接把内容交给任务；但本方案仍覆盖“从源群自动取得”的原需求。

## 3. 推荐架构：每台手机独立运行

```text
手机内配置页：源群、消息条件、目标群、每日时刻
                         ↓
AutoJs6 每日任务 → 本地任务记录 SQLite → 无障碍执行脚本
                                             ↓
                                        本机 Android 微信
                                             ↓
                                  本机进度、结果、失败记录
```

AutoJs6 安装匹配设备 ABI 的 APK，由 `tasks.addDailyTask` 注册每日任务，单个执行脚本完成源群读取和目标群操作；该 API 在本次核查的 `Tasks.kt` 中实际存在 [2]。任务状态通过 Android 本地 SQLite 保存，恢复语义与下文一致。开发方可以使用电脑开发和调试，但客户安装、配置和日常执行均在手机完成，不要求连接电脑或 ADB。

首版交付 AutoJs6 运行器、业务脚本和脚本内的简单配置页；客户通过表单录入源群、目标群和时间，查看进度，开始、暂停或停止任务。JSON 仅作为内部配置格式，不要求客户手工编辑。打包成独立品牌 APK 可以后续验证，本次预算不默认包含独立 APK 的打包、升级与兼容性适配。

首次安装时提供手机内权限引导，包括无障碍、按需启用的悬浮窗/截图权限、定时与后台运行设置。基础按钮操作优先使用控件节点，只有实际页面需要时才加入 OCR；权限被撤销或执行条件不满足时，显示原因并暂停。

每台手机同一时刻只运行一个任务。执行时会切换到微信并占用前台界面，客户不能同时手动切换页面、聊天或锁屏。到点触发定时任务不等于能在安全锁屏下直接操作微信；密码锁屏状态下需用户先解锁后执行。可以安排在客户不使用手机的时段，长任务需保证电量与网络。

多台手机先各自维护本机群清单和计划，各执行当前登录账号能够访问的群，不依赖电脑中控。如果使用同一个素材源群，各台手机的账号都必须能访问该群；原始卡片不会自动出现在其他手机里。本阶段不需要 Web 后台、Redis、分布式队列或自研 Android 执行引擎。

## 4. 完整执行流程

### 4.1 建立群清单

录入源群和目标群，给每个目标分配本地唯一标识，记录其所属设备/账号和实际显示名称。先验证每个群可以从当前账号准确进入，建议把需长期使用的群保存到通讯录。

群名不等于稳定群 ID。重名、名称截断、搜索结果含普通联系人或历史消息，都可能造成定位歧义。首版只接受可唯一定位的目标；遇到歧义就暂停该目标，不能点击第一个搜索结果继续发送。

客户应一次性确认目标清单。执行前剔除源群、检查重复目标、确认每个目标可访问。不能默认一个账号已经拥有 1,000 个可访问群。

### 4.2 到点后进入源群，选定本次消息

使用“指定源群 + 发布人 + 消息类型 + 内容关键词 + 时间窗口”筛选，而不是转发最后一个聊天气泡。

素材时间窗口锚定本次计划开始时刻，例如 18:00 任务只取 17:45–18:00 的候选；即使任务迟到或恢复，也不把窗口跟随当前时间移动。若实际界面无法可靠识别消息日期与时间，则这条自动筛选规则仍未通过验证，不能假定生效。

推荐使用固定素材源群，在任务开始前发布本次内容。若同一时间窗口里有多个符合条件的候选，首版停止并提示歧义；可以通过固定发布人或任务标记改善匹配，避免每天手工选消息。

不把系统通知当作完整的聊天记录接口。默认到点主动进入源群读取，不要求任务全天监视所有群。

### 4.3 固定本次素材，避免中途换成新消息

- 文本：保存完整原文和摘要，整轮使用同一份内容。
- 卡片：保存源消息的可见定位证据和截图。UI 自动化没有可靠的服务端消息对象快照，后续仍需定位同一条原消息；若消息被撤回或定位不确定，暂停，不能改转发刚出现的新卡片。

时间、发布人和内容摘要只能作为界面匹配依据，不能冒充微信提供的全局唯一消息 ID。

### 4.4 逐群执行，先做可核对的串行流程

卡片走“找到原消息 → 长按 → 转发 → 搜索并核对目标群 → 检查发送确认界面 → 发送”。文本走“打开目标群 → 核对群 → 输入原文 → 核对内容 → 发送”。具体菜单、节点、resourceId 以目标微信版本实测为准。

首版优先逐群执行，因为每个目标更容易独立记录、核验和恢复。验证版应另外测试原生转发页的“多选”能力：若当前版本支持且目标核对可靠，再按实测支持的批次大小优化。**不写死所谓统一的每批上限。**

定位优先级为：可验证的控件语义/结构 → 限定区域图像或 OCR → 经固定环境校准的坐标。OCR 只补缺失节点，不负责单凭相似文字决定收件群。

### 4.5 结果回读与不确定状态

点击发送不等于发送完成。应进入目标群检查本方消息、匹配内容或卡片，并检查是否出现发送失败标记。这里最多确认“客户端界面观察到已发送”，不能证明群成员已读，也不能声称取得服务端送达回执。

建议状态为：

```text
pending → ready → send_attempt_started → ui_observed
                               └──────→ confirmation_unknown
         └──→ failed_before_send
```

在产生发送动作前，先把 `send_attempt_started` 写入 SQLite。设备断开或程序重启后，保留该状态的目标按“不确定”处理：先查证，不自动重发。发送前失败可以在限定次数内重试；发送后结果不确定不能直接套用同样重试规则。

界面自动化无法把本地数据库提交和微信发送做成一个原子事务，因此不能承诺绝对“恰好一次”。这个恢复策略用于减少重复发送和误判漏发。

## 5. 定时策略

必须把两个时间概念分开：

| 时间要求 | 设计方式 |
| --- | --- |
| 每日 18:00 开始执行 | 时区固定为 Asia/Shanghai，调度在该时刻创建一轮任务 |
| 每日 19:00 前完成 | 根据群数、实测耗时与设备分配评估；到截止时间暂停余下目标并记录 |
| 某天 18:00 的任务被重复触发 | 用“任务标识 + 本次计划时刻 + 目标标识”去重 |
| 设备离线，恢复时已过执行时刻 | 配置允许的启动迟到窗口；超出窗口记为错过，避免半夜补发白天任务 |
| 上一轮还没结束，下一轮到了 | 同一设备排队，并检查截止时间，禁止两个任务争抢界面 |

主方案由手机内 AutoJs6 注册每日任务。任务开始时检查无障碍服务、网络、微信登录状态、屏幕可操作性和本机任务互斥；执行条件不满足时留下本地提示，按迟到窗口决定是否等待或跳过。不能把需要用户解锁的情况记录为已经执行成功。

设备内方案必须专门验收应用进程存活、定时权限、系统重启及锁屏后的行为。Android 官方说明 WorkManager 周期任务最短间隔为 15 分钟，实际执行时间受约束影响，不能用它保证精确到点；需要更精确的触发时，应按 AlarmManager 的适用范围与权限设计 [10][11]。AutoJs6 自身的定时能力也需按安装版本实测，不能仅凭有“定时任务”菜单承诺全天候运行。

如果设备内脚本依赖 MediaProjection 截图/OCR，Android 官方要求每个投屏会话取得用户同意；进程或会话终止后的权限恢复需要验证 [12]。因此，首次授权、系统重启和应用被清理后可能需要客户在手机上恢复运行条件，不能默认全过程不再需要任何操作。

## 6. 10、100、1,000 群如何扩展

下表的数量是**需要发送的目标群数**。如果客户说共有 10 个群且其中一个是源群，目标数量应为 9。

先按逐群操作每群 **15–30 秒**作容量估算，包含定位、发送和检查；这是估算假设，不是实测速度。卡片往返、找不到群、失败恢复都可能增加耗时。

| 目标群数 | 单设备估算耗时 | 实施策略 |
| ---: | --- | --- |
| 10 | 约 2.5–5 分钟 | 单设备完成验证，先把准确性和恢复做好 |
| 100 | 约 25–50 分钟 | 若完成窗口允许，可继续单设备；再评估多选转发是否有效提速 |
| 1,000 | 约 4 小时 10 分钟–8 小时 20 分钟 | 用实测数据核算完成窗口；有必要才按现有账号和群归属分配多设备 |

**群数不直接决定设备数，完成窗口和群归属才决定。** 不应宣称“100 群必须多设备”或“1,000 群单账号一定不行”，这些结论没有本次实测支持。

设备数的理想下限可估为：`ceil(目标群数 × 每群实测耗时 / 可用窗口秒数)`。例如假设每群 20 秒，1,000 个目标要在 30 分钟内完成，纯串行时间均摊至少需要 12 台设备；这尚未计入初始化、异常和分组约束，也不表示这些设备都能访问相应群。

多设备只按已有账号与可访问群分片，每台手机独立执行。不能默认同一微信账号可以同时在多个 Android 实例登录并并行执行。实际登录关系要在客户环境验证。若实际是多个客户各用一台日用手机，则分别按其账号、目标群和可用时段配置，不把所有手机当作可以随意调度的公共设备池。

容量验证记录每群耗时的中位数和 P95、异常恢复耗时、来源读取时间；批量转发则记录“每批耗时/实际批次人数”，不能继续套用逐群模型。

## 7. 分阶段落地与验收

### 阶段 A：固定环境验证，预计 2–3 人日

固定一台客户实际 Android 手机、Android 版本、微信版本、语言、字体、分辨率与 DPI。用客户真实类型的素材，在双方确认的 10 个目标群里跑通源群读取和转发，同时验证日用手机的定时、锁屏、后台清理及权限恢复行为。

输出一份实测结果：消息类型、可定位节点、原生多选行为、实际耗时、中文输入和卡片打开结果、失败恢复情况。若常规控件无法定位，再评估局部图像/OCR，而不是提前实现整屏视觉操作。

### 阶段 B：手机端可交付版，追加约 4–7 人日

加入手机内配置页、权限引导、群清单、每日计划、任务去重、SQLite 状态、暂停/继续、结果页和失败证据。客户在手机上完成配置，不需要编辑配置文件或使用电脑。

至少验收以下五组行为：

1. 文字与实际卡片样本分别验证；目标群正确，源群排除，文本参数不丢失。
2. 同名/改名群、多个候选源消息、源消息撤回，均不会发送到未经确认的对象。
3. 到点启动、离线迟到、重复触发、跨日任务，执行结果符合时间配置。
4. 发送前断开、点击发送后断开、应用崩溃重启：已观察成功目标跳过，不确定目标不盲目重发。
5. 连续执行三轮完整任务并核对记录；统计耗时和异常。这里的“三轮”是建议的最低验收样本，不是稳定性保证。

### 阶段 C：按测量结果扩展

先将同一套运行器和脚本安装到其他手机，各自配置账号和群清单；相同环境复用代码，新增机型按需适配，不按每台重新开发完整系统。只有客户需要在一台手机集中管理其他设备时，再评估云端任务下发和手机管理入口；这不是首版必需功能。

建议先报固定范围的验证，再根据验证结果签手机端交付。以下按 **AutoJs6 运行器 + 业务脚本 + 手机内简单配置页**、一个源群、一款固定手机环境、一类确认后的消息素材估算，以 **1,500 元/人日**作为本次示例计价假设。相比此前电脑托管估算，新增手机内配置、权限引导与定时恢复适配：

| 交付项 | 工作量估算 | 示例金额 |
| --- | --- | --- |
| 阶段 A：一款环境、实际素材、10 个目标验证 | 2–3 人日 | 3,000–4,500 元 |
| 阶段 B：在验证基础上完成手机端版本 | 追加 4–7 人日 | 追加 6,000–10,500 元 |
| 阶段 A+B 合计 | 6–10 人日 | 9,000–15,000 元 |

这是技术范围对应的估算，包含上述简单手机配置与结果页，不包含设备采购、独立品牌 APK、复杂管理界面、额外消息类型或后续微信大版本适配。验证费用是否抵扣总价应在报价单中写清；上表的合计已经包含阶段 A，不应重复加收。

对外描述可使用：

> 开发直接在 Android 手机上运行的微信群定时转发辅助工具，不要求客户配备电脑。用户在手机内设置源群、目标群和执行时间，工具到点切换至微信执行转发，提供进度、暂停、结果与中断恢复。先完成一款实际手机下的 10 群验证，再确定最终目标规模、运行条件和完成窗口。

可填写的范围与验收模板见同目录 `wechat-forwarding-quote-template.md`；配置提案见 `wechat-task.example.json`。该 JSON 是待开发系统的需求模板，不是已经可运行的 uiautomator2 或 AutoJs6 脚本。
