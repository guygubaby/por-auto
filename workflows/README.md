# 工作流 Registry v1

默认源：`https://github.com/guygubaby/por-auto`，分支 `main`。客户端直接通过 GitHub REST API 读取本仓库 `workflows/registry.json`，不需要后端或客户电脑安装 Git。

## 发布工作流

1. 新建 `workflows/<唯一标识>/workflow.json`，标识使用英文字母、数字、`-` 或 `_`。
2. 按下述格式编写工作流，调整页面文字、步骤和版本。现有示例：`wecom-open`、`wecom-nickname`、`wecom-first-chat`、`wecom-broadcast`。
3. 执行 `pnpm registry:index`，生成包含 SHA-256 的统一索引；执行 `pnpm registry:check` 检查是否同步。
4. 提交并推送工作流文件及 `workflows/registry.json`。客户在软件“工作流商店”填写仓库地址和分支，点击“添加 / 刷新仓库”，然后安装或更新相应工作流。

脚本只使用已有执行引擎能力时，无需重新发版客户端。增加新的动作类型、协议或原生能力时仍需升级客户端。客户端遇到未知动作或不兼容引擎版本会停止安装并给出提示。

## 目录约定

```text
workflows/
  registry.json
  README.md
  wecom-open/
    workflow.json
  wecom-broadcast/
    workflow.json
```

索引由脚本生成，不手工填写散列。客户端要求每项路径严格为 `workflows/<id>/workflow.json`，并校验文件内容、标识和 SHA-256；整次刷新使用同一个 Git 提交，避免拉取到新旧版本混合的文件。每个源最多 32 个工作流，文件各不超过 256 KiB，最多可配置 20 个源。

## 工作流格式

顶层字段必须包含：`schemaVersion: 1`、`minEngine: 4`（企业微信原生动作）或 `minEngine: 5`（按单聊 / 群聊分类处理全部对象）、`id`、`name`、`version`、`description`、`package`、`steps`。`package` 只能是 `com.tencent.wework`。未知字段会被拒绝。

每个步骤包含 `name` 和 `action`，推荐提供唯一且稳定的 `id`。工作流 `version` 使用 SemVer（例如 `2.0.0`），与 JSON 结构版本和 `minEngine` 分开演进。现有动作：

| type                | 参数                                       | 行为                                                                                                                                                         |
| ------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `wake`              | 无                                         | 点亮屏幕，不绕过密码锁屏                                                                                                                                     |
| `launch`            | `activity`                                 | 启动顶层 `package` 指定应用的 Activity                                                                                                                       |
| `wait`              | `ms`                                       | 有限等待；单步最多 10 秒，合计最多 30 秒                                                                                                                     |
| `tap`               | `selector`、可选 `skip_if`、`recover_back` | 唯一匹配才点击；存在跳过条件时跳过；可最多返回 3 次寻找入口                                                                                                  |
| `back`              | 无                                         | 系统返回并等待界面稳定                                                                                                                                       |
| `chat_home`         | 无                                         | 引擎 4；企业微信消息首页，确认侧栏已收起                                                                                                                     |
| `chat_profile`      | `output`                                   | 引擎 4；原生读取企业微信个人信息中的姓名                                                                                                                     |
| `chat_first_chat`   | `output`                                   | 引擎 4；打开企业微信首个普通会话                                                                                                                             |
| `chat_open_chat`    | `target`、`output`                         | 引擎 4；唯一完整名称，打开后再核对标题                                                                                                                       |
| `chat_send_text`    | `text`                                     | 引擎 4；已确认会话后提交一次文字；先核对目标和完整草稿                                                                                                   |
| `chat_broadcast`    | 无                                         | 引擎 5；企业微信按单聊 / 群聊分类批量消息，使用 `por-auto://schemas/chat-send-input/v1` 输入                                                                 |
| `read_row`          | `page`、`labels`、`output`                 | 确认页面标题，从标签同行容器读取唯一文本，写入结果字段                                                                                                       |

`selector` 可包含 `text`（精确文字候选列表）、`prefix`（文字前缀候选列表）、`bottom`（只查找屏幕底部）、`peers`（要求指定文字在同一行）。`text` 和 `prefix` 至少存在一项。`skip_if` 是选择器列表，只检查文字存在性，不使用位置约束。匹配歧义会停止，不凭猜测点击。

工作流为受约束的 JSON 脚本，不执行仓库内任意 JavaScript、Python、EXE 或 shell 命令。新流程组合已支持的动作即可。每个工作流一次最多 40 步，同手机任务按到达顺序排队，全局最多 4 台并发；页面操作前检查目标应用是否可见。固定文字发送动作每个工作流最多一次，文字 1–500 字节；批量消息支持 1–4000 UTF-8 字节；目标确认后不要插入其他导航动作。失败不会自动重发。

固定发送和批量发送合计最多一个动作，不能通过混用 `chat_send_text` 与 `chat_broadcast` 绕过限制。桌面宿主、手机控制器和 Registry 索引脚本复用 `mobile-workflows/shared/src/core.js` 的 `validateWorkflow`，统一拒绝未知字段、无效动作参数、重复步骤/输出、超限等待和不受支持的输入 Schema。批量配置按 `chat_broadcast` 能力识别，合法自定义 ID 无需包含 `broadcast`。

## 私有仓库与本地配置

私有仓库使用有该仓库 Contents 只读权限的 GitHub 访问令牌。令牌只保留在本次请求内存中，提交表单后清空，不写配置、日志或安装包。仓库不会因设为默认源而自动获得授权；客户需自行具备仓库访问权限。

应用在本地用户数据目录保存 `workflow-store.json`，包含源列表、已同步目录及已安装工作流快照；刷新目录不会自动替换已安装版本，必须点击安装/更新。同步失败时保留原有文件。运行结果保存在同目录的 `runs/`，记录工作流版本和 Git 提交。关闭应用后安装结果仍保留；已安装工作流不依赖联网运行。

默认随软件附带上述 4 个工作流，私有仓库还未授权时也可先试用。桌面运行器直接调用 uiautomator2 官方手机端服务，不依赖 Python。

## 输入、生命周期与执行快照（引擎 5）

`wecom-broadcast` 声明 `"inputSchema": {"$ref":"por-auto://schemas/chat-send-input/v1"}`。客户端只接受已实现的输入协议；Go 宿主与手机共享 JS 控制器的校验是运行事实来源；新接收配置为 `{ "direct": true, "groups": true }`，至少选择一种。旧 `scope/mode/names` 仅保留给已有固定快照，不在新配置界面提供。工作流作者不在公共 manifest 放客户的消息、接收名单或凭据。

在已安装卡片点击「配置」，分别设置：

1. **运行前 Hook**：可选 HTTP 请求，开始手机操作前执行；失败就不运行手机工作流。消息来源可选它的解析结果。
2. **运行主体**：消息可手动填写、使用前置结果，或配置独立 HTTP 请求。HTTP 可在本轮发送前获取一次，或在进入并核对每个目标会话后、输入消息前获取最新数据。无法进入目标时不执行该目标的消息请求。后者参数值可用 `{{recipient.title}}`、`{{recipient.index}}`、`{{recipient.total}}`；两者都可用 `{{device.serial}}`、`{{workflow.id}}`。

新配置按列表直接执行：群聊在群聊列表中顺序定位，单聊在首页会话列表中顺序定位，不按每个对象发起全局搜索。旧固定名称快照保留搜索兼容。完整接收名单仍在本轮处理前读取并固定。

3. **运行后 Hook**：正常完成或业务失败时执行一次，可在参数、请求头值和 JSON 请求体中使用 `{{run.id}}`、`{{run.status}}`、`{{device.serial}}` 和 `{{outputs.nickname}}` 等已存在字段。不存在的变量报错，不执行 JS 表达式。后置请求失败记录错误，绝不重跑手机动作；进程退出或显式取消不保证回调完成。

HTTP 支持 GET/POST/PUT/PATCH/DELETE、查询参数、普通请求头、JSON 请求体、Bearer/Basic/API Key（请求头或查询参数）。鉴权值保存在 macOS 钥匙串/Windows 凭据管理器，配置仅存随机引用。超时 5–120 秒、响应最多 512 KiB、请求正文最多 64 KiB；不跟随重定向、不自动重试。GET/DELETE 不发送正文；POST/PUT/PATCH 之间切换保留 JSON 正文。鉴权配置不要塞进普通参数；运行快照中的请求配置只含凭据引用，不含鉴权明文。系统凭据不可用时保存失败，不降级为明文。

解析支持 UTF-8 纯文本，或 JSON Pointer（如 `/data/message`）选出字符串；后置回调还可忽略响应，支持 204。HTTP 错误、解析失败、空内容或超限会停止发送。「测试请求与解析」只发起配置的 HTTP 请求，不操作手机；含变量时使用示例值。响应样本也可离线单独解析，不发起网络请求。

配置保存在安装实例上；更新工作流保留配置。每个定时任务冻结安装版本、输入、Hook 和执行方式；已有任务要显式更新快照才采用新配置。数据本身在每轮执行时获取，不使用测试预览作为正式消息。

发送类工作流统一正式执行，公开配置不再提供预演开关。旧发送测试快照不会自动转成真实发送：旧定时任务先暂停，桌面重新保存、手机重新创建后才能运行。旧字段仅用于识别旧任务与历史记录。正式运行的 `{{run.mode}}` 为 `send`，HTTP 接口测试为 `preview`。

执行方式固定为原生无障碍控件。旧安装或旧定时快照中的 `executionMode: "visual"` 会在运行时归一到 `native`，不会读取截图或调用图像模型。前后置 Hook、消息刷新、名单冻结和逐会话日志共用同一套生命周期。

## 目标与发送记录

勾选「群聊」时读取企业微信消息首页的「群聊」分类；勾选「单聊」时读取「全部」分类并排除群聊清单中的完整名称。群聊清单先完整枚举，用于避免同名群被误当单聊；两者合并时按完整名称去重。所谓全部是本次原生列表可枚举的全部可发送会话。逐屏读取到确定末尾后才发送；缺失、分类内同名、列表变化或无法确认末尾时停止，不把第一屏当作全部。

运行记录仅保存处理数量、当前或出错对象及必要的发送检查点，不重复保存全部成功对象。失败时保留最近 32 条事件和有限页面证据；历史最多 200 条，超出后清理最旧记录。发送意图先落盘，点击后只观察，不自动重试；中断时 `sending` 显示为 `uncertain`。停止会取消后续操作；已经提交但未完成回读的发送需人工核对。发送成功只表示 UI 已观察到新消息。

会话标题必须完整，不允许删除数字前缀或补全省略号。原生消息回读要求正文与同一消息行内的唯一右侧头像对应；接收方向、缺失方向或歧义节点不计入已发送消息。资源映射目前按企业微信 5.0.12 的既有原生节点证据维护，新版本需独立验证，不能只凭正文相同判定成功。

## 卸载

已安装工作流可单独卸载，官方 Registry 本身仍常驻。卸载意图保存在 `uninstalledKeys`，重启、同步来源不会自动装回；主动重新安装才清除。关联定时任务暂停，历史记录保留，旧快照也不能绕过卸载继续运行。

启用、保存为启用、手动触发、Cron 分发及执行器均检查安装状态；卸载与定时领取使用一致的锁顺序，已领取的批次完成前不能卸载其工作流。重新安装后才可手动启用保留的任务，其原有版本与配置快照不会被自动更新。

## 设备兼容性

运行器只使用原生无障碍节点，不使用 OCR、截图或图像模型，也没有视觉回退或盲点坐标。企业微信当前支持 `com.tencent.wework` 的简体中文原生页面，已在 vivo X21 / Android 9 / 企业微信 5.0.12 验证电脑端四个工作流。接收范围以消息首页「全部 / 群聊」分类可枚举的列表为准，功能入口不作为接收对象。空控件、重名、未确认末尾、旧草稿或提示状态缺失时停止。发送界面观察不代表网络送达。
