# 真机调试：打开微信与读取昵称

日期：2026-10-19（Asia/Shanghai）。设备：vivo X21，Android 9 / API 28，微信 8.0.79；电脑：macOS Apple Silicon。真实昵称、会话、手机序列号和截图未提交到仓库，调试数据仅在本机 `work/real-device-debug-cache/` 中。

## 复现与原因

使用实际 Rust 工作流执行器稳定复现：准备服务、唤醒及启动步骤返回成功，进入「我」时失败。检查失败前的页面与前台窗口后，确认微信实际上已打开，但其无障碍树只有一个不可见、无类名、无尺寸的空节点。旧版把它当成有效页面并尝试返回恢复，退到桌面后才报“目标应用不在前台”。系统自带 `uiautomator dump` 也无法读取微信节点，增加等待或改用活动窗口根节点未解决。

新版资料页使用「个人资料」「名字」，旧流程仅接受「个人信息」标题。开启 AutoJs6 或手机自带朗读服务时，vivo 系统要求登录 vivo 账户；用户当前无法完成该验证，最终方案没有依赖该授权。[上游同类问题及服务兼容经验](https://github.com/openatx/uiautomator2/issues/1099)只作为排查线索，结论以上述本机复现为准。

## 修复

- 启动后轮询实际前台窗口，启动命令成功不再等于步骤成功。保留 `launch.txt`。
- 统一检测空应用节点，停止无效返回和点击；微信发送路径也使用该检查。
- 兼容两种个人资料页标题，保留昵称唯一值校验。
- 对**与内置昵称步骤完全一致**的工作流允许本机 OCR 兼容：截图增强对比度、识别控件文字和位置、复用唯一目标/底部同排标签校验。仅重新读取页面以等待过渡状态，不重放点击。发送工作流不启用此路径。
- 原始控件树、识别后的结构、文字位置和启动信息可随运行 JSON 一并导出。结果明确标注截图识别及特殊字符限制。

macOS 构建时用系统 Swift 编译 Vision 辅助程序并嵌入客户端，客户不需要 Swift、Python 或其他解释器。Windows 使用系统 Windows PowerShell / WinRT OCR，需要简体中文 OCR 语言功能；图片在本机处理。

## 验证

- 原始执行器的昵称流程可复现同一失败；空节点回归测试先失败、修复后通过。
- 修改后的真实执行器完成「打开微信」，并断言微信确为前台窗口。
- 修改后的真实执行器完成全部昵称步骤，返回值与资料页截图中的名字逐字一致；无障碍授权保持未开启。
- 单元测试覆盖空节点拦截、前台窗口解析、新版资料标题、视觉行分组、XML 转义、放大识别去重，以及现有发送保护。

可再次运行只读真机检查（仅允许随包的打开/昵称步骤，拒绝修改后的步骤和发送流程）：

```sh
cargo run --manifest-path src-tauri/Cargo.toml --example device_smoke -- \
  "$POR_DEVICE_SERIAL" "$POR_ADB_PATH" src-tauri/resources/u2.jar \
  workflows/wechat-nickname/workflow.json
```

## 限制

截图识别不是应用内部字段 API，表情、装饰文字及低对比度字体可能不能完整识别；结果需结合截图核对。只验证了上述手机和两个工作流，发送、其他机型以及 Windows 真机连接另行验收。Windows 原生图像识别有独立 CI 自检；运行器未安装 OCR 语言时会明确跳过识别并输出警告，不算通过实际识别验证。
