# 助手为什么老失败，以及怎么改成能「自己找办法」的循环

参考实现：phongent 的 `core/agent/`（`AgentLoop`、`RetryPolicy`、`StuckAdvice`、`StopRules`、`OutcomeJudge`）。

## 我们现在的循环

`assistant/AgentRunner.kt` 每一步：读屏 → 让模型给一个 JSON 动作 → 执行 → 再读屏。判失败的方式是几条硬规则：

| 现在 | 触发条件 | 结果 |
|---|---|---|
| 画面没变 | 连续 2 步 hash 相同 | 直接抛异常结束 |
| 重复动作 | 同一个动作 4 次 | 直接抛异常结束 |
| 解析失败 | 模型回的不是合法 JSON | 直接抛异常结束 |
| 模型报错 | 任何 HTTP 失败 | 直接抛异常结束 |

问题在于：**这些情况本来都是可以纠正的**，我们却当成终局。模型不知道刚才那步为什么没用，也没机会换别的目标。

## phongent 的做法（可以直接借的四点）

1. **提醒，而不是停止。** `StuckAdvice` 在「没有进展」的第二次起，才在工具结果里附一条建议（"换个思路，找不到就如实放弃"），而不是立刻结束；`StopRules` 只在连续多次、模型仍然没有新动作时才收尾。
2. **错误先分类，再决定要不要重试。** `RetryPolicy` 只对 429 / 5xx / 网络错误退避重试（带 Retry-After、指数退避 + 抖动、单任务总等待预算 5 分钟）；Key 错、额度、模型名、内容被拒、解析失败——重试也没用，直接交给模型或用户。
3. **把失败当输入喂回去。** 每次工具调用的结果（成功/失败/画面没变/已重复）都进入下一轮上下文，模型据此自纠。
4. **结局分类清楚。** `TaskState.Failed(kind)` 区分「放弃」「守卫叫停」「模型出错」「步数用完」，运行记录里能看出到底卡在哪一类。

## 建议改造（按投入从小到大）

### 一、把「失败」改成「反馈」（核心，改动集中在 AgentRunner）

每一步执行后判定效果，并把判定写进下一轮的提示：

```
动作: tap(12)          → 结果: 画面没变化
动作: input(5,"你好")  → 结果: 输入框内容已变成「你好」
动作: back             → 结果: 回到了列表页
```

具体规则：

- 画面没变：先**重读一次屏幕**再判断（动画/加载会误判），仍没变就给出「这一步没有效果」的反馈，让模型换动作；
- 同一动作重复：反馈「你已经点过第 12 项，画面没变」，要求换目标；
- 解析失败：把「你上次的输出不是合法 JSON，这里是原文」回给模型，让它重发（最多 2 次）；
- 模型 HTTP 错误：按类别重试（见下），仍失败才终止。

**停止条件**从「2 步 / 4 次」改成「连续无进展 4 次」或「同一个动作第 3 次」，并且每次先给一次纠正机会。

### 二、模型调用的重试策略

照 `RetryPolicy` 写一个 40 行的版本：429/5xx/网络 → 退避重试（1s、2s、4s，带抖动，最多 3 次）；401/403/404/额度 → 立刻停并给出人话原因（现在只显示「HTTP 401」，看不出该改什么）。

### 三、让模型自己「规划—验证」

在提示词里加一条：**每次动作必须带一个 `expect` 字段**（"点完之后应该看到什么"）。执行后拿 `expect` 和实际画面比，不一致就把差异喂回去。这比我们的 hash 比较精确，也能让模型自己发现选错了目标。

### 四、预算代替上限

- 单任务步数上限（60 步，软上限，到 50 步开始提醒"快点收尾"）；
- 单任务重试等待预算 5 分钟；
- 连续无进展 4 次 → 结束并说明卡在哪一屏、试过哪些动作（现在只说一句"界面连续两步没有变化"）。

### 五、把过程记下来

每一步的 `动作 / 预期 / 实际 / 判定` 写进运行日志并随日志上报，服务端 `/runs/<id>` 能直接看到它在哪一步开始打转——这是之后调提示词的唯一依据。

## 预期效果

现在「找不到输入框」这类问题会直接终止；改完之后模型会先试别的定位方式（滚动、返回再进、点搜索），实在不行才放弃，并且放弃时能说清楚试过什么。真正不可恢复的（口令错、模型 401）仍然立刻停。
